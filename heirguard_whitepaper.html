1. Executive Summary

1.1 The Problem in Depth

Cryptocurrency ownership introduces a fundamental problem that traditional finance solved through intermediaries: what happens to assets when the owner dies?

In traditional finance: bank accounts have beneficiaries, investment accounts have transfer on death (TOD) designations, life insurance has named beneficiaries, real estate passes through probate court, and retirement accounts have designated beneficiaries.

In cryptocurrency: no beneficiary designation exists at the protocol level, private keys die with the owner with no recovery mechanism, exchanges freeze accounts upon death notification, multi-sig requires pre-death coordination and doesn't solve inheritance, and paper wallets are lost or destroyed with no backup.

2. Problem Statement & Market Analysis

2.1 The Technical Problem

Private keys are bearer instruments. Anyone who possesses a private key controls the associated funds. Unlike a bank account with a beneficiary form, there is no native mechanism in blockchain protocols to designate a successor.

Mathematical framing:

Let K be the private key. Let F(K) be the funds controlled by K. If the owner of K dies, there exists no function Transfer(F(K), H) where H is an heir, without the owner's consent during life.

HeirGuard introduces a new primitive: A time-locked transfer that executes automatically after a user-defined number of blocks without a "proof-of-life" transaction.

4. Solution Overview

4.1 Core Mechanism

HeirGuard implements a dead-man's switch using Canopy's block-height timer.

State Machine Diagram:

No Will ──create_will──→ Active Will Active Will ──reset_timer──→ Active Will Active Will ──timer expires──→ Expired Will Active Will ──cancel_will──→ Cancelled Will Expired Will ──claim_will──→ Completed Will

4.2 User Flow

Phase 1: Will Creation

  1. User connects wallet (BLS12-381)
  2. User specifies: heir address, amount to lock, timer duration (blocks), optional message
  3. User signs create_will transaction
  4. Transaction submitted to Canopy RPC (POST /v1/tx)
  5. Plugin executes DeliverMessageCreateWill: deducts amount, creates vault, stores in state

Phase 2: Proof of Life (Ongoing)

  1. User periodically submits reset_timer transaction
  2. Plugin verifies owner signature, updates LastResetHeight and StreakCount
  3. Timer resets to full duration

Phase 3: Death or Inactivity

  1. User stops resetting timer
  2. After TimerBlocks pass without reset, will enters "expired" state
  3. Heir submits claim_will transaction
  4. Plugin verifies heir address and timer expiry
  5. Plugin transfers locked CNPY to heir

8. Mathematical Proofs & Formal Verification

8.1 Timer Expiry Proof

Theorem: A will becomes claimable by the heir if and only if the owner has not reset the timer for a duration of at least T blocks, where T is the timer duration set at creation.

Proof:

Let Hc = current block height, Hl = last reset block height, T = timer duration.

Active condition: Active(Hc, Hl, T) ⇔ (Hc - Hl < T)

Expired condition: Expired(Hc, Hl, T) ⇔ (Hc - Hl ≥ T)

Reset function: reset(S, Hc) → Hl = Hc

Claim function: claim_heir(H) → if Expired(Hc, Hl, T) then Transfer(F(K), H)

8.2 Security Proof: No Double Claim

Theorem: A vault cannot be claimed more than once.

Proof: Let C be the claim flag in the vault state. Initially C = false. When claim_will executes, if C = false and Expired(Hc, Hl, T) then Transfer(F(K), H) and C = true. Any subsequent claim_will transaction will see C = true and reject.

8.3 Security Proof: Owner-Only Reset

Theorem: Only the owner can reset the timer.

Proof: During CheckTx for reset_timer, if msg.OwnerAddress != vault.OwnerAddress, reject. During signature verification, if VerifySignature(msg.Signature, msg.OwnerAddress) != true, reject.
